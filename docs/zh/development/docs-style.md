# 文档撰写规范

本规范约束 `docs/` 下全部文档与 README 的撰写、维护与双语同步，目标读者是**贡献者**（人类与 AI 代理同等适用）。规范的总原则：文档以代码和发布工作流为准，宁可短而准确，不可长而过时。

## 文档体系与分工

| 文件                            | 受众             | 内容边界                                                                |
| ------------------------------- | ---------------- | ----------------------------------------------------------------------- |
| `README.md` / `README.zh-CN.md` | 所有访客         | 项目定位、特性概览、快速开始、文档导航、反馈社区；不放开发细节          |
| `CONTRIBUTING.md`（双语）       | 贡献者           | 流程规范：issue / 分支 / 提交 / PR / 发版                               |
| `AGENTS.md`                     | 贡献者与 AI 代理 | 编码规范唯一事实源：风格、注释、接口、门禁                              |
| `docs/zh                        | en/usage/`       | 最终用户                                                                | 按功能域组织的使用指南（快速开始、对话与 Agent、Harness、MCP…） |
| `docs/zh                        | en/development/` | 开发者                                                                  | 开发环境、架构、扩展指南、本规范                                |
| `docs/zh                        | en/reference/`   | 二者之间                                                                | 配置参考、权限模型等查询型材料                                  |
| `CHANGELOG.md`                  | 所有用户         | 面向用户的版本变化记录（Keep a Changelog 精神：按版本、讲人话、给链接） |

## 双语镜像规则

- `docs/zh/` 与 `docs/en/` **逐文件对应**：一侧新增/改名/删除文档，另一侧在同一 PR 内同步。
- 实质内容变更必须双侧同步；纯笔误修复也建议双侧一起改。
- 英文侧不是机器直译：术语、语气按英文技术文档习惯写（参考现有 `docs/en/` 的行文），但**事实、结构、链接目标必须与中文侧一致**。
- README 双语与 CONTRIBUTING 双语遵循同样的对应规则。
- 校验：`npm run check:docs` 会遍历两侧所有 Markdown 链接（含锚点）——它是同步的最低保障，不是全部；结构性改动需人工对照。

## 写作规范

- **结构**：每篇文档以 `# 标题` 开头，H2 组织主题，H3 细分；同级标题不跳级。超过三级的嵌套通常意味着该拆文档了。
- **段落与列表**：操作步骤用有序列表；特征枚举用无序列表；每个列表项保持同构（都是短句或都是完整句）。表格用于「多维度对照」（模式表、配置项、支持矩阵）。
- **代码块**：标注语言（`bash / `rust / ```tsx）；只放可复制运行的命令与最小可用示例，不放假代码；行内代码用反引号包裹标识符、命令、路径。
- **链接**：站内文档用相对路径链接（`[聊天与 Agent](../usage/chat-and-agent.md)`）；引用章节用锚点（锚点拼写需过 `check:docs`）；外链给规范 URL。
- **措辞**：
  - 描述「是什么/怎么用」，不写营销语（「强大」「完美」）；
  - 避免未兑现的承诺（"即将支持"、"将来会"）——未交付的能力要么不写，要么明确标注状态；
  - 版本敏感的表述带上版本号（"自 v0.8 起"）。
- **截图**：仅用于界面说明；**禁止出现**个人数据、真实会话内容、本机绝对路径、API Key；用空白档案或虚构演示内容，统一 1600x1000 webp 存放于 `docs/assets/screenshots/`，从文档相对链接。
- **称呼与语气**：面向用户用「你」不用「您」；面向开发者用第一人称复数或无人称句。

## 维护纪律

- **文档随代码**：行为变更的 PR 附带对应文档更新（PR 模板有此项）；只改代码不改文档视为未完成。
- **删除优先于注释**：功能下线时同步删除其文档段落，不留「历史遗留」章节——历史归 CHANGELOG 与 git。
- **一次性产物不入库**：中间报告、审查记录、阶段性计划、环境问题记录不写入 `docs/`；它们属于 PR 描述、issue 或本地笔记。`docs/` 只保留随产品演进的常青文档。
- **数据与示例**：文档中的示例数据一律虚构（`demo-project`、`example.com`、`your-api-key`），禁止从真实环境复制。
- **校验清单**：文档改动后运行 `npm run check:docs`；CHANGELOG 改动后确认双语键值无涉（CHANGELOG 单语维护）。
